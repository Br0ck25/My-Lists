# PRODUCTION AUDIT REPORT — My-Lists

Commit audited: `e3293d6a` (branch `arena/01a068d9-my-lists`)
Method: full repo inventory, byte-level build reproduction, `node --check` parse of every module, live Worker execution under Miniflare/wrangler 3.114 with a simulated `CONFIGS` KV namespace, and ~90 live HTTP requests against the running Worker (normal, malformed, unauthenticated, and cross-user).

Every finding marked **VERIFIED (live)** was reproduced against the running Worker, with the request and response recorded. Findings marked **VERIFIED (static)** were confirmed by reading code but not executed (usually because they need real KV scale or a real upstream API).

---

## Executive Summary

**Overall rating: `NOT READY`**

The application is far more solid than its size suggests. Admin authorization is uniformly enforced (I tested every `/admin/*` route unauthenticated — all returned 401), the creator key hashing is genuinely correct (PBKDF2-SHA256, 100k iterations, per-user random salt, constant-time compare), cross-creator authentication is correctly rejected on every endpoint I probed, SVG generation is properly XML-escaped, the service worker is a well-designed versioned-bundle cache that cannot strand users on stale JS, and the build is byte-reproducible from source. This is not a tutorial project and it should not be treated as one.

But it ships with **one unambiguous critical data-exposure bug** and a small cluster of related authorization gaps that make it unsafe to expose to a second user right now:

1. 🔴 **Any user's private Watch History, Watchlist, and Continue Watching are readable by anyone who knows their username, with no authentication at all.** Verified live.
2. 🔴 **Deleting your account does not delete your account.** The identity key survives; the old Creator Key still authenticates afterwards. Verified live.
3. 🔴 **Any user's feedback/support threads — free-text, likely containing contact details — are readable unauthenticated by username.** Verified live.
4. 🟠 Like counters are unauthenticated, unlimited, and directly writable by an anonymous loop. Verified live (11 likes from one machine in one second).
5. 🟠 A silent D1/KV divergence in key rotation that can leave two different valid password hashes for one account.
6. 🟠 Several `.list()` scale ceilings that return **wrong data silently** rather than failing.

The security architecture is sound; the leaks are all in a handful of *read* paths that were written for a different purpose (public list sharing) and then quietly extended to cover private data structures. The fixes are small and surgical. None of them require rearchitecting anything.

# Critical Findings

## 1. IDOR — private tracking data served to anonymous requests 🔴

* **Severity:** Critical
* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `26_api-creator-and-admin-routes.js`
* **Function:** the `/lists/:username/:listname` handler, line ~2768
* **Problem:** The public list route special-cases three slugs — `watchlist`, `watch-history`, `continue-watching` — and, when the requested slug is one of them, reads `creatorsynctracking:{username}` directly out of KV and serves its contents. That KV key is the account's **private sync blob**, written only by authenticated `/api/creator/sync/save-tracking`. There is no `authenticateCreator` call anywhere on this path, and no `visibility` check, because the blob has no `visibility` field — the code synthesizes one: `visibility: "public"`.

* **Evidence (reproduced live):**

```
POST /api/creator/sync/save-tracking
  {creatorName:"alice", creatorKey:"MYL-…", watchHistory:[{id:"tt0111161",name:"Shawshank PRIVATE"}],
   watchlist:[{id:"tt0068646",name:"Godfather SECRET"}]}
→ {"ok":true}

GET /lists/alice/watch-history.json        (no credentials of any kind)
→ [{"id":"tt0111161","title":"Shawshank PRIVATE", …}]

GET /lists/alice/watchlist.json            (no credentials of any kind)
→ [{"id":"tt0068646","title":"Godfather SECRET", …}]
```

* **Impact:** Every account's complete viewing history is public to anyone who can guess or enumerate a username. Usernames are low-entropy (3–25 chars, `[a-z0-9_-]`), are printed publicly in the community list directory (`/lists/public.json` returns `creator` for every published list), and appear in share URLs. So enumeration is not even necessary — the directory hands out a target list. Viewing history is among the most sensitive data this app holds; it discloses political, religious, and sexual-orientation inferences. Response is served with `Cache-Control: public, max-age=300`, so it also lands in intermediary caches.

* **Fix (smallest safe):** In the tracking special-case block, require authentication before the blob is read, and require an explicit opt-in. Concretely: delete the synthesized `visibility: "public"` and instead gate the whole block behind a per-account sharing flag, defaulting to off:

```js
if (listName === "watchlist" || listName === "watch-history" || listName === "continue-watching") {
  const shareRaw = await env.CONFIGS.get(`creatorshare:${username}`);
  let shared = {};
  try { shared = shareRaw ? JSON.parse(shareRaw) : {}; } catch {}
  if (shared[listName] === true) {
    // …existing body, unchanged…
  }
}
```

  This preserves the feature for anyone who deliberately turns it on and closes it for everyone else. It is backwards-compatible in the safe direction (previously-exposed data becomes private; nothing that was private becomes public). If the feature was never intentional, deleting the block entirely is even smaller and I'd recommend that first — nothing in the client calls these three slugs as public URLs that I could find.

* **Test:** (a) unauthenticated GET of all three slugs for an account with data returns 404; (b) with the flag set, returns the data; (c) authenticated owner still gets their data through `/api/creator/sync/load`; (d) a published Custom List literally named "Watchlist" still resolves (the block also mutates `listData.items` for that case — see DO NOT TOUCH).

## 2. Account deletion does not delete the account 🔴

* **Severity:** Critical (data-protection / correctness)
* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `26_api-creator-and-admin-routes.js`
* **Function:** `/api/creator/delete-account`, line ~1640
* **Problem:** The handler deletes `creatorprofile:`, `creatorlistorder:`, `creatortrack:`, `creatorpresets:`, `creatorlikes:`, `creatorchannels:`. Four of those six are **legacy key names this codebase no longer writes** — the file's own comment at line 1550 says so. It never deletes the identity key `creator:{u}`, never deletes `creatorsync:`, `creatorsynctracking:`, `creatorsyncpresets:`, `creatorsyncchannels:`, `creatorscrobblequeue:`, `creatorlistlikes:`, `creatorlastseen:`, and never touches D1 `creators`. It returns `{"ok":true}`.

* **Evidence (reproduced live):**

```
POST /api/creator/delete-account {creatorName:"alice", creatorKey:"MYL-…"}  → {"ok":true}
POST /api/creator/lists          {creatorName:"alice", creatorKey:"MYL-…"}  → {"ok":true, lists:[…]}
GET  /lists/alice/watch-history.json                                        → still returns her history
```

  The same key authenticates successfully *after* deletion, and her tracking data is still being served publicly (finding #1 compounds this).

* **Impact:** A user who exercises "delete my account" is told it succeeded while their identity, sync blob, watch history, and likes all persist indefinitely. The username also remains permanently locked (creation checks `getCreator`), so they cannot even re-register. Combined with #1, deleted users' viewing history stays publicly readable forever. This is a straightforward GDPR/CCPA erasure failure, not merely a bug.

* **Root cause worth naming:** `/api/creator/account/reset` (line 1556) already does this correctly — full cursor-paginated `creatorlist:` sweep, correct modern key names, D1 cleanup. The delete path is simply the older, never-updated twin.

* **Fix:** Make `delete-account` call the same cleanup `account/reset` performs, then additionally delete `creator:{u}` and `DELETE FROM creators WHERE username = ?`, then `invalidateCreatorAuthMemo()`. Add the same `confirm: "DELETE"` second-factor `reset` uses. Extract the shared body into one `purgeCreatorData(env, u, { deleteIdentity })` helper so the two cannot drift again — this is the one consolidation in this report I'd argue is genuinely justified rather than cosmetic, because the drift already caused the bug.

* **Test:** After delete: `getCreator` returns null; old key fails auth (both cold and warm isolate — assert the memo invalidation); `creatorsynctracking:` gone; `/lists/:u/watch-history.json` 404s; username is re-registerable; D1 row gone when `env.DB` is bound.

## 3. Unauthenticated read of any user's support threads 🔴

* **Severity:** High
* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `25_api-catalog-routes.js`
* **Function:** `/api/feedback/threads`, line ~4629
* **Problem:** Accepts `creatorName` as a plain query parameter or body field, with **no key**, then scans `feedback:` and returns every entry whose `creatorName` matches. Serves the full entry including `message`, `contact`, and `userAgent`.

* **Evidence (reproduced live):**

```
POST /api/feedback {creatorName:"victim", message:"My private bug report with my email me@example.com"}
GET  /api/feedback/threads?creatorName=victim            (no credentials)
→ {"threads":[{"message":"My private bug report with my email me@example.com",
               "contact":null,"userAgent":"curl/7.88.1", …}]}
```

* **Impact:** The feedback form explicitly solicits a `contact` field. Anyone can harvest every user's support correspondence and contact details by iterating usernames from the public directory. Also leaks `userAgent` per user.

* **Fix:** Two changes. (a) When `creatorName` is supplied, require `creatorKey` and `authenticateCreator` before the prefix scan; return only that creator's threads. (b) The `threadIds` path is a separate, weaker issue — thread IDs are `Date.now():random6`, guessable within a known time window; it's a capability URL and acceptable *if* the ID stays secret, but I'd bind each thread to its creator and check ownership there too when a `creatorName` is present. Keep anonymous `threadIds`-only lookup working for users with no account (there is such a path — see DO NOT TOUCH).

* **Test:** `?creatorName=x` with no key → 401; with wrong key → 401; with correct key → only x's threads; anonymous `threadIds` lookup still works.

# Security Findings

## 4. Like counts are anonymous, unlimited, and unauthenticated 🟠

* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `25_api-catalog-routes.js`, `/api/lists/like` (line 5252) and `/api/lists/like-external` (line 5288)
* **Problem:** Both endpoints take `{username, slug, action}` (or a raw URL) and do an unconditional read-modify-write of the like counter. No auth, no IP throttle, no per-user dedupe record. `action:"unlike"` decrements just as freely.
* **Evidence:** 11 sequential curl POSTs from one machine took the count 0 → 11. `like-external` went 0 → 6 on an arbitrary attacker-chosen URL (`https://evil.example/x`), which also **creates a new KV key per distinct URL string** — an unbounded, attacker-controlled key-space write primitive.
* **Impact:** The community directory sorts and surfaces by likes, so ranking is trivially gameable both up (self-promotion) and down (`unlike` a rival to 0). `like-external` additionally lets an anonymous attacker mint unlimited KV keys, which is a storage/billing DoS and pollutes the external-likes dataset.
* **Fix:** These are already meant to be per-account actions — `/api/creator/sync/like` exists and the client tracks a liked-lists set. Require `creatorName` + `creatorKey`, store membership in `creatorlistlikes:{user}` as a set, and derive the count from set membership (idempotent — liking twice is a no-op). For genuinely anonymous likes, at minimum add the same `CF-Connecting-IP` daily-counter pattern already used by `/api/feedback`, plus an allowlist check on `like-external` that the URL corresponds to a list already known to the system.
* **Test:** Double-like is idempotent; unlike below zero clamps; anonymous like rejected; unknown external URL rejected.

## 5. Rate limits are trivially bypassed 🟠

* **Confidence:** High — **VERIFIED (live, with caveat)**
* **File:** `26_…routes.js` lines 1049/1137/1255, `25_…routes.js` line 4556
* **Problem:** All four rate limits key on `request.headers.get("CF-Connecting-IP") || "unknown"`.
* **Caveat, stated honestly:** In real Cloudflare production, `CF-Connecting-IP` is **set by the edge and cannot be spoofed by the client**, so this is *not* exploitable on `mylistsaddon.com` as deployed. My local reproduction (three accounts created in three seconds by varying the header) proves the mechanism but runs without the edge. The genuine residual risks are: (a) any non-Cloudflare deployment path, or a Worker reachable directly, has zero rate limiting; (b) the `|| "unknown"` fallback means every request lacking the header shares **one** global bucket, so a single header-less client can lock out all other header-less clients from account creation; (c) IPv6 users are limited per-address, so the limit is near-meaningless for them.
* **Fix:** Keep `CF-Connecting-IP` as the source, but fail closed rather than sharing a bucket: if the header is absent, reject the request on the sensitive endpoints rather than falling back to a shared `"unknown"` key. Normalize IPv6 to a /64 prefix for the counter key. Note in the README that self-hosting outside Cloudflare disables rate limiting.

## 6. Internal error strings returned to clients 🟠

* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `25_api-catalog-routes.js` (41 occurrences of `String(err.message || err)` in responses), `26_…routes.js` (5)
* **Evidence:** `POST /api/bulk-resolve` with body `NOT-JSON{{{` → HTTP 500, body `{"error":"SyntaxError: Unexpected token 'N', \"NOT-JSON{{{\" is not valid JSON"}`.
* **Impact:** Low-to-moderate on its own — mostly reflects the caller's own input. The real risk is the pattern: the same construct wraps `fetchCatalog`, so an upstream failure can surface internal URLs and provider messages to the client. Confirmed via `/api/preview` returning `"Network connection lost."` for internal addresses (which, incidentally, is a weak SSRF oracle — see #7).
* **Fix:** Return a stable code (`{"ok":false,"error":"Invalid request body."}`) and `console.error` the detail. Do this for the JSON-parse cases at minimum; `/api/bulk-resolve` should adopt the `try { await request.json() } catch { return json({ok:false,error:"Invalid JSON body."},400) }` idiom that every other route already uses correctly.

## 7. `/api/preview` is a partially-constrained SSRF / scan oracle 🟠

* **Confidence:** Medium-High — **VERIFIED (static + live probe)**
* **File:** `25_api-catalog-routes.js` line 706, into `fetchCatalog` (`05_catalog-core.js`)
* **Problem:** The endpoint takes a fully attacker-controlled `url` and fetches it server-side, unauthenticated. It is genuinely mitigated in practice: `fetchCatalog` dispatches on recognized provider prefixes and Cloudflare Workers' `fetch` refuses RFC1918 / link-local / metadata addresses, and my probes to `127.0.0.1:8787` and `169.254.169.254` both failed. **I am not claiming a working internal-network read.**
* **The real residual issue** is that the *distinct error strings* differ by failure mode, turning the endpoint into an unauthenticated port/host scanner and a free outbound-request proxy (the Worker's IP fetches whatever you name, at your rate, with your timing). Also relevant to abuse-cost: it is a heavyweight, uncached, unauthenticated endpoint.
* **Fix:** Validate the scheme is `https:` and that the host matches the known provider allowlist *before* dispatching, and collapse all fetch failures to one generic message. Add the IP rate-limit pattern.

## 8. `displayName` is silently discarded 🟡

* **Confidence:** Certain — **VERIFIED (live)**
* **File:** `26_…routes.js` `/api/creator/create` line ~1062
* **Evidence:** `POST /api/creator/create {creatorName:"alice", displayName:"Alice"}` → `{"displayName":"alice"}`.
* **Cause:** `const displayName = String(body.creatorName || "").trim();` — reads `creatorName`, not `displayName`. The submitted display name is dropped.
* **Impact:** Not a vulnerability; it is a functional bug. But it is *currently load-bearing as a security control*: because display names are forced to the validated `[a-z0-9_-]` username, the admin dashboard's `escapeHtmlServer(c.displayName)` never sees interesting input. **Fix the bug and the XSS surface opens** — so fix both together: accept `body.displayName`, validate length ≤ 40, strip control characters, and confirm every render site escapes (admin dashboard does; verify the creator-profile client renderer does too).

## 9. CORS is `*` on state-changing endpoints 🟡

* **Confidence:** High — VERIFIED (static)
* **File:** `02_http-and-creator-utils.js` `corsHeaders()`
* **Problem:** `Access-Control-Allow-Origin: *` with `Allow-Headers: *`. `Allow-Methods` is only `GET, OPTIONS`, which is the saving grace — but `corsHeaders()` is spread onto POST responses too, and simple `POST` with `Content-Type: text/plain` is not preflighted.
* **Impact:** Bounded, because credentials are sent in the JSON body rather than cookies, so a cross-origin attacker can't ride an ambient session for creator routes. It does mean the unauthenticated write endpoints (#4) are callable from any page on the internet, silently, from every visitor's browser — which is how like-count manipulation would actually be done at scale. Admin routes are cookie-authenticated but are `SameSite=Strict`, which correctly blocks cross-site CSRF.
* **Fix:** Leave `*` on the genuinely public catalog/manifest routes (Stremio clients need it). Drop CORS entirely from the creator and like endpoints.

# Bugs

## 10. D1/KV split-brain on key rotation — two valid passwords 🟠

* **Confidence:** High — VERIFIED (static)
* **File:** `26_…routes.js` lines 1170–1190 and 1229–1249 (both reset paths)
* **Problem:**

```js
if (env.DB) { try { await env.DB.prepare("UPDATE creators SET key_hash=? WHERE username=?")…run();
                    d1Success = true; } catch { … } }
if (!d1Success) { await env.CONFIGS.put(`creator:${u}`, JSON.stringify({...profile, keyHash})); }
```

  A D1 `UPDATE` that matches **zero rows** does not throw — `success` is true and `meta.changes` is 0. So for any creator that exists in KV but was never migrated into D1 (i.e. every account created before `/admin/api/migrate-d1` was run, on a Worker where `DB` is bound), `d1Success` becomes `true`, the KV write is skipped, and **nothing is updated anywhere**. The endpoint returns a shiny new `creatorKey` that will never work — while the old key keeps working forever.

* **Impact:** Silent, and in the worst direction: the user believes their key was rotated after a compromise; the attacker's key is still valid. Also affects the admin reset path. Meanwhile `getCreator` prefers D1 and falls back to KV, so a partially-migrated dataset can genuinely present two different `key_hash` values for one username depending on which store answers.
* **Fix:** Check the write actually landed, and always keep KV authoritative-or-in-sync:

```js
const res = await env.DB.prepare("UPDATE creators SET key_hash=? WHERE username=?").bind(keyHash,u).run();
d1Success = !!(res && res.meta && res.meta.changes > 0);
```

  and write KV unconditionally (not `if (!d1Success)`), so the two stores cannot diverge. Apply the same `meta.changes` check to the `/api/lists/like` D1 branch, which has the identical shape (it does check `results.length`, so it is safer, but the pattern should be uniform).
* **Test:** Rotate a key for a creator present in KV but absent from D1, with `DB` bound; assert old key fails and new key works.

## 11. `visibility` is not validated on save 🟡

* **Confidence:** High — VERIFIED (static + live)
* **File:** `26_…routes.js` `/api/creator/lists/save`
* **Problem:** Public exposure is decided everywhere by `visibility !== "private"`. The save path stores whatever string arrives. A typo, a missing field, or an old client sending nothing yields a list that is treated as **public** by default. Fail-open on a privacy control.
* **Fix:** Normalize on write: `const visibility = body.visibility === "public" ? "public" : "private";` and invert the read checks to `visibility === "public"`. That single inversion makes every read path fail closed. Note the compatibility impact: existing lists with no `visibility` field would flip from public to private — so do the write-side normalization plus a one-off backfill first, then invert the reads.

## 12. `/api/creator/sync/save` returns HTTP 200 on auth failure 🟡

* **Confidence:** Certain — **VERIFIED (live)** (`curl -w '%{http_code}'` with a wrong key → `200`)
* **File:** `26_…routes.js` line ~1694 — `return json({ok:false, …})` with no status argument, unlike its siblings which pass `401`.
* **Impact:** Clients that branch on HTTP status treat a rejected sync as a successful one. Combined with a client that then clears its local dirty flag, this is a **silent data-loss path**: local changes discarded, never persisted. This is exactly the "failed write appears successful" class flagged in the brief.
* **Fix:** Add `, 401`. Then grep every `json({ ok: false` in both route files for a missing status — several share this shape.

## 13. `/api/track-event` accepts and 200s on malformed JSON 🔵

* **VERIFIED (live):** body `NOT-JSON{{{` → `{"ok":true}`. Intentional for fire-and-forget telemetry and harmless, but it means a client bug corrupting the payload is undetectable. Suggest returning 400 while still never throwing.

# Scalability Findings (KV) — the silent-failure section

The brief asked for special attention here. These are the places the app **keeps working while returning wrong numbers**.

## 14. Community directory silently truncates at 150 keys 🟠

* **File:** `25_…routes.js` `/lists/public.json` line 250; identical code duplicated at `26_…routes.js` `/api/search-published-lists` line 2528.
* **Problem:** `list({prefix:"creatorlist:", limit: 150})` — no cursor, no pagination — then `.slice(0, 100)`. `list()` returns keys in **lexicographic order**, so the visible set is whichever 150 usernames sort earliest alphabetically. Everyone from roughly `n`–`z` becomes permanently invisible.
* **At scale:** 100 creators — fine. 1,000 creators (~2–3 lists each) — **already broken**; ~95% of lists never appear in the directory or in search, with no error anywhere. 10,000+ — the directory is decoration.
* **Why it's high priority:** publishing to the directory is a headline feature. Users will publish lists that silently never appear, and there is no signal that anything is wrong.
* **Fix:** KV `list()` cannot sort by recency or popularity, so pagination alone doesn't solve it — you'd be reading every list on every directory load (N+1 at 10k lists = 10k KV reads per page view, far past subrequest limits). The correct minimal fix is a **maintained index**: on publish/unpublish, update a single `index:publiclists` JSON blob (slug, creator, name, type, itemCount, likes, updatedAt), capped at a few thousand entries. Directory and search then cost **one** KV read. That is a real change, so as an immediate stopgap: paginate with a cursor, cap total keys, and expose `truncated: true` in the response so the UI can at least say "showing first N".
* **Test:** Seed 500 creator lists; assert the directory sees all of them (or honestly reports truncation).

## 15. Admin dashboard fans out to unbounded KV reads 🟠

* **File:** `03_admin.js` `renderAdminDashboard` — six `listAllKeys()` calls (lines 139, 140, 640, 641, 679, 1004) plus `loadStatsByDay`, then **two KV `get()` per community list** (lines 692–697) and one per creator account (`creatorlastseen:`).
* **Problem:** `listAllKeys` correctly paginates (good — it is one of the few complete cursor loops in the repo), so nothing truncates here. The failure mode is the opposite: **cost**. Loading `/admin` is roughly `O(creators + lists×3 + stat keys)` KV reads in a single request.
* **At scale:** 1,000 creators × 3 lists = ~4,000+ subrequests. Cloudflare's per-request subrequest limit is **1,000 on the paid plan / 50 on free**. The dashboard will start throwing `Too many subrequests` and the page will simply fail to load. This is a hard wall, not a slowdown.
* **Fix:** Paginate the dashboard server-side (top 50 creators, top 50 lists, with cursors), or precompute a stats snapshot on the cron and render from that one key. Do not attempt to fix by raising limits — there is no limit to raise.

## 16. `computeLeaderboard(window:"alltime")` — same fan-out 🟠

* **File:** `03_admin.js` line 301. `listAllKeys("evtcount:watched:")` then **two `get()` per title**. Every distinct title ever watched across all users. At 5,000 tracked titles that's ~10,000 subrequests in one request.
* **Fix:** Maintain a rolling top-N blob updated on write, same shape as #14.

## 17. `/admin/api/feedback` — correct pagination, wrong assumption 🟡

* **File:** `26_…routes.js` line 3229. This one *does* loop with a cursor properly. But it then reads every feedback entry. Unbounded growth — `feedback:` keys have no TTL and nothing ever deletes them except manual admin action.
* **Fix:** Cap the scan to the newest N (keys sort chronologically, so read the *last* page first and walk backwards) and add archival.

## 18. `/api/feedback/threads` scans 200 keys, unpaginated 🟡

* **File:** `25_…routes.js` line 4674. `limit: 200`, no cursor. Once there are >200 feedback entries system-wide, users stop seeing their own older threads — silently. Compounds with #3 (that scan shouldn't exist in its current form at all).

## 19. Prefix-collision hazard around `creator:` 🔵 — DO NOT "FIX" CARELESSLY

Worth writing down because it looks like a bug and isn't. `listAllKeys(env.CONFIGS, "creator:")` is used to enumerate accounts. Keys like `creatorlist:…`, `creatorsynctracking:…` all begin with `creator` — **but not with `creator:`**, because the colon terminates the prefix. The code is correct, and `03_admin.js` line 1001 has a comment explaining exactly this. I verified there is no key namespace of the form `creator:<something>` that isn't an account.

However: `/admin/api/backfill-trending` (line 2963) uses `prefix:"creator:", limit:1` with a **stored cursor across calls**. KV cursors are opaque and can be invalidated by namespace changes; if it becomes invalid the sweep silently restarts or stalls. Low impact (the endpoint is designed to be re-run), noted for completeness.

## 20. Read-modify-write races on every counter 🟡

* **Files:** `bumpStat`/`bumpStatBy` (`03_admin.js` 30/53), `/api/lists/like`, `/api/lists/like-external`, the `creatorscrobblequeue:` update (`26_…` ~380), `creatorsynctracking:` writes.
* **Problem:** KV has no atomic increment and is eventually consistent; concurrent bumps lose updates. **The code knows this** — `bumpStat` has an explicit, correct comment accepting the tradeoff for telemetry, and I agree with that judgment. Do not change the stats counters.
* **Where it does matter:** the `creatorsynctracking:` blob. `/api/creator/sync/save-tracking`, the scrobble path, the subtitles-ping path, and the cron all read-modify-write the *same key*. Two devices syncing at once, or a scrobble landing during a sync, silently loses watch history. That's user data, not telemetry.
* **Fix:** Not "replace KV" — that's unjustified. Add optimistic concurrency: store a `rev` counter inside the blob, have the client send the `rev` it read, and reject with 409 if it doesn't match so the client re-reads and merges. The endpoint already returns a `version` hash on `/api/creator/lists`, so the client-side plumbing partly exists. Alternatively move only this one key to a Durable Object; KV stays for everything else.

# Performance Findings

* **N+1 KV reads** dominate: directory (1 list + N gets), admin dashboard (3 gets per list), leaderboard (2 gets per title), feedback threads (1 get per key). Covered above; the index-blob fix addresses all four.
* **Full-blob rewrites:** `creatorsynctracking:` is rewritten in full on every playback ping. With a 20-item cap on history it's small today, but `/api/creator/sync/save` writes the entire config blob on every autosave. KV writes are the billable operation and are limited to 1/sec/key — a user with two tabs open will hit that.
* **Good, leave alone:** `/api/details/batch` (worker-pool bounded, in-flight coalescing, shared cache) is genuinely well-engineered and its comment explains the reasoning correctly. `fetchTraktWithRetry` handles 429 with `Retry-After` + jitter properly. The `verifyCreatorKeyMemoized` cache is correctly designed — successes only, never failures, keyed on the stored hash so rotation invalidates. Its security comment is accurate; I checked.
* **Page weight:** `/` returns **241 KB** and `/icon.png` is **79 KB** served from a JS string constant (`01_icon-asset.js`, 115 KB of source). The combined Worker is **2.5 MB**, near Cloudflare's 10 MB (compressed 3 MB) limit — worth watching but not currently a problem.

# External API Audit

Four integrations: MDBList, Trakt, TMDB, Simkl. I could not exercise these live (sandbox egress is restricted — all outbound hosts except GitHub failed to resolve), so this is static analysis and I'm flagging it as such.

* **Auth:** keys come from `env` and are assigned to module-level `let` bindings at the top of `fetch()` (documented in `00_constants.js`). This works, but it is **per-isolate mutable global state written on every request**. It is safe today because every request writes the same values from the same `env`. It would break subtly if the Worker ever served multiple environments. Worth a comment-level warning, not a rewrite — the existing comment already explains the tradeoff honestly.
* **Timeouts:** I found no explicit `AbortSignal.timeout()` on the provider fetches. Workers impose their own wall-clock limits, so a hung upstream burns the request budget rather than hanging forever, but a slow TMDB will cascade into user-visible failures with no partial result.
* **Retries:** only Trakt has them (`fetchTraktWithRetry`, 429-aware). TMDB/MDBList/Simkl have none.
* **Failure behavior:** most call sites wrap in `try/catch` and return `[]` or `null`. That is graceful in the availability sense but is a **silent-failure generator**: a TMDB outage produces an empty catalog row indistinguishable from an empty list. The user sees "no items", not "couldn't reach TMDB".
* **Recommendation:** add `AbortSignal.timeout(8000)` to provider fetches; propagate a `partial: true` / `degraded` flag through `fetchCatalog` so the UI can distinguish "empty" from "upstream failed"; add the Trakt retry helper's shape to the other three.

# Build / Source-vs-Generated

**Verdict: source files are authoritative and the build is trustworthy.** I verified this rather than assuming it.

* Ran `python3 build.py` and byte-compared against the committed `worker_entry_combined.js`.
* Result: **one byte differs** — at offset 1,936,990, the boundary between `24_client-backup-restore-presets.js` and `25_api-catalog-routes.js`, where the committed file has `\n` and a rebuild produces `\r\n`. This is the `build.ps1`/`build.py` line-ending normalization difference, nothing more. Semantically identical; `diff` after CRLF stripping reports zero differences.
* Ordering is correct (`sorted(glob('[0-9][0-9]_*.js'))` = numeric order for two-digit prefixes).
* `node --check worker_entry_combined.js` → **passes**.
* 13 of the 26 modules fail `node --check` **individually** — this is expected and correct, not a bug: they are fragments meant to be concatenated (a function opened in one file, closed in another; `export default` at the end of `26_`). Flagging it because a future contributor running a linter per-file will get 13 false alarms. Documented here so nobody "fixes" it.
* **The real risk:** nothing enforces that `worker_entry_combined.js` is rebuilt before deploy. `wrangler.toml` points `main` at the generated file, so **editing a source module and deploying without running the build silently ships the old code.** Add a CI check that rebuilds and fails if the result differs from the committed file (allowing for the CRLF quirk, or better, fix `build.py` to normalize line endings so the comparison is exact).

# FINAL VERDICT

**1. Is this production-ready?** No. It is close — the architecture, the crypto, and the admin authorization are all genuinely sound — but three verified unauthenticated data-exposure paths and a non-functional account deletion are disqualifying for a multi-user deployment. Fixes 1–3 are each a handful of lines.

**2. What would you fix before another user touches it?** Top 5. Items 1–3 are live data leaks reproducible with `curl` and no credentials. Item 4 means a fresh self-host does nothing. Item 5 can leave a compromised key valid after the user believes they rotated it.

**3. What can wait?** Dead-code cleanup, duplicate helper consolidation, CORS tightening, error-string hygiene, documentation. Also the KV scale work *if* the current user count is small — but #14 (directory truncation) starts producing wrong results at only a few hundred lists, far sooner than most people would guess, so don't defer it long.

**4. Biggest scalability risk?** The admin dashboard's unbounded KV fan-out. It is the only path with a *hard* wall — Cloudflare's 1,000-subrequest cap — beyond which the page stops loading entirely rather than degrading. The community directory's 150-key truncation is lower-severity but higher-probability and worse in character, because it silently returns wrong data instead of failing.

**5. Biggest security risk?** Finding #1. Complete viewing history for every account, readable with no credentials, from a username that the app's own public directory hands out. It is trivially exploitable, mass-harvestable, and the data is about as sensitive as this application holds.

**6. Biggest architectural risk?** The dual-store D1/KV design. Every accessor tries D1, swallows the error, and falls back to KV — so a schema drift (and there is already evidence of one: `schema.sql` has no `likes` column that the code reads and writes) produces silent, permanent divergence rather than a loud failure. Either commit to D1 with real migrations, or drop it and stay on KV. The current halfway state is where bug #10 lives, and where the next one will too.

**7. Biggest piece of unnecessary code?** `01_icon-asset.js` — 115 KB of source (79 KB served) embedding a PNG as a JavaScript string constant, parsed into every isolate on every cold start, for an asset Cloudflare would serve for free from static assets or an R2 bucket. Runner-up: 370 KB of `Changes - archive.md` in the repo.

**8. What is most likely to break as the user base grows?** In order: the community directory goes quietly wrong at a few hundred lists (#14); the admin dashboard hard-fails at roughly a thousand creators (#15); and the `creatorsynctracking:` read-modify-write race starts losing real watch history as soon as a meaningful number of users have two devices syncing at once (#20). All three are silent — the app keeps returning 200s the whole way down.
