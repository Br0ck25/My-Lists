# PRODUCTION AUDIT REPORT

**Repository:** https://github.com/Br0ck25/My-Lists
**Date:** 2026-09-05
**Scope:** Full production-readiness audit — 27 source modules (~112k lines), 1 combined Worker, ~120 routes, all KV operations, all external API integrations, build pipeline, PWA, docs.
> **Remediation status lives in [`AUDIT-2026-09-05-STATUS.md`](AUDIT-2026-09-05-STATUS.md), not here.**
> This report is the point-in-time record of what was found on 2026-09-05 and is deliberately
> left unedited as findings get fixed, so the evidence and the reasoning stay intact. The
> tracker is the file that changes.

**Method:** Every finding below was verified by execution against the repo's own test harness (`tests/harness.mjs`) or by direct code trace. Findings I could not execute are labelled as code-verified. Nothing here is asserted from pattern-matching alone.

## Executive Summary

### Overall rating: **READY WITH FIXES**

This is a genuinely well-engineered codebase. The things that usually go wrong in a project this size are already right: every `/admin/*` route is authenticated, every `/api/creator/*` route scopes its KV keys to the *authenticated* username rather than a body parameter (no IDOR), passwords use PBKDF2-100k with timing-safe comparison, CORS is deliberately narrowed to the routes that need it, the CSP is real, OAuth uses PKCE + state cookies with timing-safe validation, private lists are correctly filtered from the public share route, and the build is byte-reproducible with CI drift detection. The `verify.sh` pipeline passes clean: no build drift, 58/58 tests green.

The problems that remain cluster into one theme, and it is the theme the audit brief singled out: **silent failure under concurrency and under abuse.** Nothing crashes. Requests return `200 OK`. Users and the operator are simply shown, or silently sold, wrong data.

The four findings that block production:

1. **`/api/track-event` is an unauthenticated, unrate-limited, permanent KV key-minting primitive.** One request mints 100 attacker-named keys. Those keys are then enumerated *and individually read* on every admin analytics load, 1:1. ~600 anonymous requests push the admin panel past Cloudflare's 1,000-subrequest cap and permanently break it, with no in-app way to clean up.
2. **A like silently reverts a creator's list edit.** `/api/lists/like` reads the whole list record, spends several KV round-trips on the vote ledger, then writes its *stale* snapshot back over whatever landed in between.
3. **The Continue Watching cron silently destroys watch history.** Same read-modify-write shape, but the window is TMDB network I/O, and the blob is the user's entire tracking state.
4. **`/api/publish-list` accepts unauthenticated, uncapped, permanent writes.** A single request stored a 4.5 MB list with 20,000 items, and there is no route that can ever delete it.

Beyond those, the admin dashboard's numbers are not trustworthy at any real traffic level: the stat counters are non-atomic read-modify-writes (20 concurrent page views recorded as **1**), and the "Top Community Lists" panel in KV-only mode reports the alphabetically-first 100 lists as though they were the most popular.

**Biggest single risk:** the trio of unauthenticated write endpoints (`/api/track-event`, `/api/publish-list`, `/api/save`). They are cheap to abuse, permanent in effect, and have no cleanup path.

## Critical Findings

### 1. `/api/track-event` — unauthenticated unbounded KV key-space write; permanently bricks the admin analytics panel

- **Severity:** Critical · **Confidence:** Certain (executed)
- **File:** `25_api-catalog-routes.js:4885` (route) → `03_admin.js:750` (`computeCatalogAndCommunityLeaderboards`), `03_admin.js:~700` (`bumpStat`), `03_admin.js` (`recordTrackedEvent`)
- **Function:** `/api/track-event` handler

**Problem.** The route has no authentication and no rate limit. It accepts 50 events per request and, for `list-copy`, does:

```js
const slug = String(e.id || "").trim().slice(0, 100);
if (slug) return bumpStat(env, `list_copy:${slug}`);
```

`slug` is arbitrary caller-supplied text with **no charset validation at all**. Each distinct value mints two permanent KV keys (`stats:list_copy:<slug>:total` and `:<day>`). `catalog-add` is the same shape — `sanitizeStatGroupName` restricts the *charset* but not the *value set*, so any 40-char alphanumeric string is a new key. `recordTrackedEvent` likewise mints `evtcount:` / `evtmeta:` / `evtdayindex:` keys under arbitrary ids.

**Evidence (executed).** One unauthenticated request:

```
HTTP 200 {"ok":true}
KV keys minted by ONE unauthenticated request: 100
sample key: "stats:list_copy:SPAM-<img src=x onerror=alert(1)>-0:total"
```

`computeCatalogAndCommunityLeaderboards` then enumerates that prefix and issues **one `get()` per key** inside a single `Promise.all`. Measured against `/admin/api/analytics?section=catalogs_lists`:

```
spam keys=   50   HTTP 200   KV get()=50     list()=4   total subrequests=54
spam keys=  300   HTTP 200   KV get()=300    list()=4   total subrequests=304
spam keys= 1200   HTTP 200   KV get()=1200   list()=5   total subrequests=1205
```

Perfectly linear. The code comment at `03_admin.js:783` already worried about "eventually cross the 1,000 cap" and concluded the key set is "bounded by real copy activity, not by list count." That premise is false — it is bounded by *nobody*.

**Impact.**
- ~600 anonymous requests (60k keys) put every admin analytics load far past Cloudflare's 1,000-subrequest-per-invocation limit. The panel throws and **stays** broken; no route deletes `stats:*` keys.
- The Trending / Most Copied / Installed Catalogs panels render attacker-chosen strings.
- Unbounded permanent KV storage and write-operation billing.

**Fix (smallest safe).** Three independent changes, each worth doing:
1. **Validate `list_copy` slugs the same way `catalog_add` names already are** — apply `sanitizeStatGroupName` (or `slugifyServer`) to `e.id` and drop anything that fails. This alone removes the markup-in-key-name problem.
2. **Bound the key space.** Only count a `list_copy` slug that corresponds to a list that actually exists (`creatorlist:*` / `publishedlist:user:*`), exactly as `/api/lists/like` already does before creating a ledger — that route's comment states the principle: *"otherwise a ledger (and a permanent KV key) could be created for any username/slug pair someone cared to invent."* Same rule, same reason.
3. **Bound the read side** so a large key set can never break the dashboard: cap the enumeration in `computeCatalogAndCommunityLeaderboards` (e.g. `listAllKeys` → a bounded `list({limit})`, or fold copy counts into the existing `index:publiclists`).

Add a per-IP rate limit on `/api/track-event` matching `/api/preview`'s existing `ratelimit:preview:${ip}` pattern.

**Test.** Assert that 50 `list-copy` events with non-slug ids mint zero KV keys; assert `/admin/api/analytics?section=catalogs_lists` issues a bounded number of subrequests with 5,000 `stats:list_copy:*` keys present.

### 2. `/api/lists/like` silently reverts a concurrent creator save

- **Severity:** Critical (silent data loss) · **Confidence:** Certain (executed)
- **File:** `25_api-catalog-routes.js:5424-5490`
- **Function:** `/api/lists/like` handler

**Problem.** The handler parses the entire list record up front, then calls `applyLikeVote` — which does up to 4 attempts of *read ledger → write ledger → re-read ledger* — and only then writes the whole record back:

```js
let likeData = JSON.parse(likeRaw);          // T0: snapshot
...
const { count } = await applyLikeVote(...);  // several KV round-trips
if ((likeData.likes || 0) !== count) {
  likeData.likes = count;
  await env.CONFIGS.put(likeKey, JSON.stringify(likeData));  // T1: stale snapshot wins
}
```

`applyLikeVote` was carefully hardened against losing *votes* (it re-reads and retries). The record write it feeds was not given the same treatment, and it clobbers **list content**, not just the count.

**Evidence (executed, ordered trace).** A creator saves 5 items while a like is in flight:

```
[like]   read list record (2 items)
[save]   WROTE list record -> items=5
[like]   WROTE list record -> items=2

FINAL stored items = 2   likes = 1
*** CREATOR'S 5-ITEM SAVE WAS SILENTLY REVERTED TO 2 ITEMS ***
```

Both requests returned `200 OK`. Nothing is logged.

**Impact.** Any visitor liking a list at the moment its owner saves it silently rolls the list back to its pre-edit state. The creator sees a successful save; the data is gone. Popular lists — the ones most likely to be edited *and* most likely to be liked — are the most exposed.

**Fix (smallest safe).** Do not write the snapshot. Re-read the record immediately before the write and update only the one field:

```js
if ((likeData.likes || 0) !== count) {
  const freshRaw = await env.CONFIGS.get(likeKey);
  if (freshRaw) {
    try {
      const fresh = JSON.parse(freshRaw);
      fresh.likes = count;
      await env.CONFIGS.put(likeKey, JSON.stringify(fresh));
      likeData = fresh;                     // index update below uses fresh fields
    } catch { /* leave the count on the ledger only */ }
  }
}
```

This narrows the window from "several KV round-trips" to "one get + one put" and, critically, stops a like from ever carrying stale `items` back to storage. **Risk: Low** — no API-contract change, no key change.

**Test.** The ordered-trace harness above, asserting `items.length === 5` after the like completes.

### 3. Continue Watching cron silently destroys user watch history

- **Severity:** Critical (silent data loss) · **Confidence:** Certain (executed)
- **File:** `07_source-fetchers-tmdb-simkl.js:1714-1821` (`checkForNewEpisodes`), invoked from `scheduled()` at `26_api-creator-and-admin-routes.js:4038`
- **Function:** `checkForNewEpisodes`

**Problem.** Per account, the sweep reads the full tracking blob, then performs **TMDB network I/O** for each candidate show, then writes the whole blob back:

```js
const syncRaw = await env.CONFIGS.get(`creatorsynctracking:${username}`);   // T0
blob = JSON.parse(syncRaw);
for (const showId of fullyWatched) {
  next = await findNextAiredEpisodeForShow(...);   // TMDB /find + /season — seconds
}
await env.CONFIGS.put(`creatorsynctracking:${username}`, JSON.stringify(blob));  // T1
```

`/api/creator/sync/save-tracking` has an elaborate, well-reasoned rescue-merge (`26_...:1846-1975`) that preserves server-side scrobbles from being wiped by a stale *client* push. That merge is one-directional. The cron does the reverse — a stale *server* write over a fresh client save — and has no merge, no re-read, and no compare-and-set.

**Evidence (executed, ordered trace).** Gating the cron at its sweep read, with a user save landing in the window:

```
[cron] read tracking blob (1 history item)
[user] WROTE tracking blob -> watchHistory=2
[cron] WROTE tracking blob -> watchHistory=1

FINAL watchHistory = 1
user's newly-watched movie still present? false
```

The item the user just marked watched is gone. Both operations succeeded.

**Impact.** The cron is documented to run every 6 minutes (`wrangler.toml`), sweeping 25 accounts per tick. On a deployment with ≤25 accounts, **every** account is swept 240×/day. A user watching something while a sweep is mid-flight loses that entry — plus any `airingNext` and `curatedRecommendations` computed since the cron's read. The loss is invisible: no error, no log, the app just quietly forgets.

**Fix (smallest safe).** Re-read and merge immediately before the write, mirroring what `save-tracking` already does in the other direction:

```js
if (blobChanged || stillFullyWatched.length !== fullyWatched.length) {
  const freshRaw = await env.CONFIGS.get(`creatorsynctracking:${username}`);
  let target = blob;
  if (freshRaw) {
    try { target = JSON.parse(freshRaw); } catch { target = blob; }
  }
  // Only the two fields this sweep actually computes:
  target.continueWatching = continueWatching;
  target.fullyWatchedShowIds = stillFullyWatched;
  target.updatedAt = Date.now();
  await env.CONFIGS.put(`creatorsynctracking:${username}`, JSON.stringify(target));
}
```

Writing only the fields the cron owns — rather than the whole snapshot — is the actual fix; the re-read closes the remaining gap. **Risk: Low.**

**Test.** The gated-cron harness above, asserting the user's post-read save survives.

### 4. `/api/publish-list` — unauthenticated, uncapped, permanent, undeletable

- **Severity:** High · **Confidence:** Certain (executed)
- **File:** `25_api-catalog-routes.js:5388-5421`

**Problem.** No auth, no rate limit, and no bound on `items` count, item size, or `name` length:

```js
const plItems = Array.isArray(plBody.items) ? plBody.items : [];
...
await env.CONFIGS.put(plKey, JSON.stringify({ name: plBody.name || baseSlug, ..., items: plItems, ... }));
```

**Evidence (executed).**

```
HTTP 200 {"ok":true,"listName":"spam-list", ...}
stored key: publishedlist:user:spam-list   value bytes: 4548996
items stored (no cap applied): 20000
```

4.5 MB accepted from one anonymous request. KV's per-value ceiling is 25 MB, so a single request can store ~5× that again.

**Impact.**
- Unbounded permanent storage and billing from anonymous callers.
- Public lists are pushed into `index:publiclists` (`updatePublicListIndex`), so spam displaces legitimate lists in the directory — the index is capped at `PUBLIC_INDEX_MAX = 20000` and sorted by likes then `updatedAt`, so *fresh* zero-like spam outranks older zero-like real lists.
- **No deletion path exists.** `/api/creator/lists/delete` is creator-scoped; there is no admin route that deletes an anonymous published list. Once written, it is permanent.
- Large `name` values also inflate every entry in the single `index:publiclists` value; if that value crosses 25 MB the `put` throws and is swallowed by `updatePublicListIndex`'s `catch`, silently freezing the directory.

**Fix.**
1. Cap inputs: `items.slice(0, 1000)`, `String(name).slice(0, 120)`, and reject items whose serialized size exceeds a sane per-list budget (the client never legitimately sends more).
2. Add a per-IP rate limit (reuse the `ratelimit:creatorcreate:${ip}` pattern).
3. Add an admin delete route for `publishedlist:user:*` so spam is recoverable. **Risk: Low** — caps are additive; existing lists are unaffected.

**Test.** Assert a 20,000-item publish is rejected or truncated to the cap; assert the second publish from one IP inside the window is rate-limited.

## Security Findings

### 5. Missing rate limits on unauthenticated write and fan-out endpoints
- **Severity:** Medium · **Confidence:** High (route inventory, executed)

Rate limiting exists and is well implemented — on `/api/preview`, `/api/feedback`, `/api/creator/create`, `/api/creator/reset-key`, `/api/creator/restore`, and `/admin/login`. It is absent on every one of these unauthenticated endpoints:

| Route | Why it matters |
|---|---|
| `/api/publish-list` | Permanent KV writes (finding 4) |
| `/api/track-event`, `/api/track-search` | Permanent KV writes (finding 1) |
| `/api/save` | Permanent KV write per call, no expiry |
| `/api/details/batch` | 60 TMDB calls/request against the operator's shared key |
| `/api/bulk-resolve` | TMDB fan-out against the shared key |
| `/api/recommendations` | Provider fan-out against the shared key |
| `/api/external-list/create` / `/delete` / `item-mutate` | Provider writes |

The shared-key endpoints let an anonymous caller burn the operator's TMDB/Trakt/MDBList quota. **Fix:** apply the existing per-IP counter pattern. **Risk: Low.**

### 6. Creator key transmitted in the URL query string
- **Severity:** Low (accepted design constraint) · **Confidence:** High

`/api/scrobble` authenticates via `?creator=…&key=MYL-…` (`26_...:448-470`). Query strings land in Cloudflare's request logs and any intermediary's. This is largely forced — Plex/Jellyfin/Emby webhooks cannot set custom headers — so it is a reasonable trade, but it should be **documented as such** in the README rather than left implicit, and the docs should tell users to rotate the key via `/api/creator/reset-key` if a webhook URL leaks.

### 7. Internal exception text returned to clients
- **Severity:** Low · **Confidence:** High

~40 handlers return `json({ ok:false, error: String(err.message || err) })`. I traced every `throw new Error(...)` in the fetch paths (`04`, `06`, `07`, `25`, `26`) and they are all deliberately status-only — no URLs, no API keys — so **no credential leak exists today**. But this is one careless `throw` away from becoming one, and it contradicts the policy the codebase states for itself at `/api/bulk-resolve`: *"Logged, not returned — the message can carry upstream URLs and internal detail that the caller has no business seeing."* **Fix:** apply that same rule uniformly — `console.error` the detail, return a generic message.

### Verified NOT vulnerable
These were tested and are correctly implemented — recorded so nobody "fixes" them:
- **No IDOR.** Every `/api/creator/*` route derives its KV keys from `auth.username`, never from a body field. Verified by extracting the key template of every route.
- **No XSS.** `escapeHtmlServer` / `escapeHtmlAdmin` both escape `& < > " '`; admin-rendered user content (feedback, creator names) is escaped at every interpolation. The badged-poster SVG escapes via `escapeXml`, and its text inputs come from `formatAirDateBadge`, which only ever returns a fixed set of tokens.
- **No SSRF / open redirect.** `/api/poster-badge` gates on `isAllowedPosterUrl` (https + host allowlist) before both the redirect and the fetch. All other redirects are `${url.origin}`-bound.
- **No config-id enumeration.** `generateShortId` is 9 CSPRNG bytes (72 bits). The stored API keys and OAuth tokens behind `/{config}/configure` are not guessable.
- **No admin auth gaps.** All 16 `/admin*` routes call `isAdminRequest`; the cookie is HMAC-signed over its expiry with `ADMIN_KEY`, `HttpOnly; Secure; SameSite=Strict`, and compared timing-safely.
- **No private-list exposure.** `/lists/:user/:slug` filters on `isPublicListVisibility`, and Watchlist/Watch History/Continue Watching require an explicit `=== true` opt-in in `creatorshare:{username}`.
- **OAuth** uses PKCE + a state cookie compared with `timingSafeEqualHex`.

## Bugs

### 8. Duplicate `handlePosterImgError` — the wrong definition wins, breaking three of five call sites
- **Severity:** Medium · **Confidence:** Certain (executed)
- **Files:** `16_client-row-core.js:800` and `23_client-list-management.js:825`

Both are top-level `function` declarations in the **same** served client script. Confirmed empirically against the rendered bundle:

```
DUPLICATE top-level fn declarations IN THE SERVED CLIENT SCRIPT: 5
    closeModal x2   escapeAttr x2   escapeHtml x2   handlePosterImgError x2   showModal x2

handlePosterImgError winner: 23_client-list-management.js (uses img.nextElementSibling)
```

The two implement **different DOM contracts**:
- `16_`'s *creates* a `.live-preview-poster-placeholder` div and appends it to the parent.
- `23_`'s assumes a pre-existing sibling placeholder: `const ph = img.nextElementSibling; if (ph) ph.style.display = 'flex';`

`23_` is later in concatenation order, so it wins everywhere. Only **one** of the five call sites (`23_:1102`) actually emits that sibling placeholder. The other four do not:

| Call site | Element after the `<img>` | Result when the poster fails |
|---|---|---|
| `23_:1102` | the placeholder div | correct |
| `19_:3150` | nothing | poster hidden, no placeholder — empty gap |
| `22_:2933` | `.cw-remove-btn`, then `.list-card-count-overlay` | **the ✕ remove button is force-shown in the poster's place** |
| `22_:3208` | same | same |
| `16_:855` | (assigned via `newImg.onerror`) | no placeholder created |

The overlay case is worse than cosmetic: `.list-card-count-overlay.mobile-only` / `.desktop-only` are toggled by a media query (`09_page-shell.js:1683-1695`), and an inline `style="display:flex"` overrides both — so the "N ›" count badge renders on mobile **and** desktop simultaneously.

**Fix.** Keep one definition. The `23_` implementation is the better one (it strips `S03E01` from episode titles and handles numeric TMDB ids), so: delete `16_client-row-core.js:800-830`, and make the fallback branch self-sufficient rather than assuming a sibling —

```js
const ph = img.nextElementSibling;
if (ph && ph.classList.contains('live-preview-poster-placeholder')) {
  ph.style.display = 'flex';
} else if (img.parentElement && !img.parentElement.querySelector('.live-preview-poster-placeholder')) {
  const el = document.createElement('div');
  el.className = 'live-preview-poster live-preview-poster-placeholder';
  el.innerHTML = '<small style="color:var(--muted); font-size:0.7rem;">No poster</small>';
  img.parentElement.appendChild(el);
}
```

That satisfies both contracts and stops the class check from ever touching an unrelated sibling. **Risk: Low.**
**Test:** render a watchlist card with a broken poster URL; assert the remove button is not force-shown and a placeholder appears.

### 9. Stat counters are non-atomic — the admin dashboard's numbers are not real
- **Severity:** Medium–High (silent wrong data) · **Confidence:** Certain (executed)
- **File:** `03_admin.js` (`bumpStat`, `bumpStatBy`, `recordTrackedEvent`, `recordSearchQuery`)

```js
const [totalRaw, dayRaw] = await Promise.all([get(totalKey), get(dayKey)]);
const total = (parseInt(totalRaw, 10) || 0) + 1;
await Promise.all([put(totalKey, String(total)), put(dayKey, String(day))]);
```

Read-modify-write with no compare-and-set. **Evidence (executed):**

```
20 concurrent GET / requests
stats:pageviews:total recorded = 1   (expected 20)
```

A 95% undercount at trivial concurrency. In production this is *worse* than the harness shows, for two compounding reasons: KV reads are edge-cached (values can be up to ~60s stale), so every request inside a cache window reads the same number and writes the same `n+1`; and KV permits only **one write per second per key**, which `stats:pageviews:total` will exceed on any busy deployment.

**Impact.** Pageviews, installs, playback pings, API-usage counts, catalog-add and list-copy counts, and the trending leaderboards all under-report by an amount that *grows with traffic* — the dashboard looks most wrong exactly when the numbers matter most. Nothing indicates this; the panel renders a confident, precise, wrong number.

**Fix.** KV cannot do atomic counters. Options in increasing order of effort:
1. **Cheapest honest fix:** label these panels as sampled/approximate in the UI so the operator is not misled.
2. **Better:** shard the hot keys — write to `stats:{kind}:{day}:{0..15}` picked at random, sum the 16 on read. Removes both the lost-update and the 1-write/sec ceiling at the cost of 16 reads per panel.
3. **Correct:** move counters to D1 (already an optional binding) with `UPDATE … SET n = n + 1`, which is atomic.

I recommend (2) — it is contained, needs no new binding, and preserves the existing read path's shape. **Risk: Medium** (changes stored key layout; needs a migration or a read-both-shapes transition, which `migrate-day-counts` already establishes a pattern for).

### 10. Admin "Top Community Lists" reports a lexicographic sample as "top" (KV-only mode)
- **Severity:** Medium (silent wrong data) · **Confidence:** Certain (executed)
- **File:** `03_admin.js:833`

```js
const listResult = await env.CONFIGS.list({ prefix: "creatorlist:", limit: COMMUNITY_CAP }); // 100
```

The D1 path does this correctly (`ORDER BY likes DESC … LIMIT 100`). The KV fallback takes the **first 100 keys in lexicographic order**, then sorts *those* by likes. The comment — *"the panel shows 100 lists, so there is no reason to read every list in the system to get there"* — is sound for D1 and wrong for KV: you cannot get the top 100 by likes from an arbitrary 100.

**Evidence (executed).** 150 public lists; the genuinely most-liked one (9,999 likes) sorts last alphabetically:

```
lists returned: 100
top entry reported: "List 0"  likes = 1
is the real #1 (9999 likes) present? false
```

**Fix.** Use the index that already exists and already carries `likes`, and is already sorted by likes (`sortPublicIndexEntries`):

```js
const idx = await getPublicListIndex(env, null);
if (idx) {
  communityListsRaw = idx.filter((e) => e.isCreator && (e.itemCount || 0) > 0)
                         .slice(0, COMMUNITY_CAP)
                         .map((e) => ({ slug: e.slug, name: e.name, creatorName: e.username,
                                        type: e.type, likes: e.likes || 0,
                                        itemCount: e.itemCount, updatedAt: e.updatedAt }));
} else { /* existing bounded scan as last resort */ }
```

This also *removes* 100 per-list KV `get`s from the dashboard. **Risk: Low.**
**Test:** the 150-list fixture above, asserting the 9,999-like list is ranked first.

### 11. N+1 KV reads on every playback ping
- **Severity:** Medium (performance) · **Confidence:** High (code-verified)
- **File:** `26_api-creator-and-admin-routes.js:410`

```js
const listKeys = await env.CONFIGS.list({ prefix: `creatorlist:${auth.username}:` });
for (const k of (listKeys.keys || [])) {
  const rawList = await env.CONFIGS.get(k.name);   // one get per list, every ping
  ...
}
```

Every scrobble ping enumerates and fully reads **every one of the creator's lists** to find their watchlist — even though the canonical key `creatorlist:{username}:watchlist` is written directly elsewhere (`26_...:1836+`). The scan exists to also catch a list the user manually named "Watchlist", which is a fair goal but not worth O(lists) reads per ping. It also has no `limit`/cursor, so it silently truncates at KV's 1,000 default.

**Fix.** Read `creatorlist:{username}:watchlist` directly; fall back to the scan only when that key is absent. **Risk: Low.**

### 12. Orphaned KV on account deletion → recycled username inherits stale like counts
- **Severity:** Low–Medium (data integrity) · **Confidence:** High (code-verified)
- **File:** `02_http-and-creator-utils.js:1492` (`purgeCreatorData`)

`purgeCreatorData` is otherwise thorough and well-motivated, but its `dataKeys` list omits two keys the app actively writes:
- `listlikevoters:{username}:{slug}` — one per list that was ever liked (`25_...:5459`)
- `scrobbleseenusers:{username}` (`26_...:1013`)

Because `delete-account` removes `creator:{u}`, the username becomes re-registrable. A new owner who creates a list with the same slug inherits the **previous owner's like ledger**: the list shows a like count it never earned, and everyone in the old ledger is silently unable to like it.

**Fix.** Enumerate and delete `listlikevoters:{u}:*` in the same cursor loop that already sweeps `creatorlist:{u}:*`, and add `scrobbleseenusers:${u}` to `dataKeys`. **Risk: Low.**
Also: `creatortrack:${u}` is listed under the *"legacy names, harmless if absent"* comment, but it is a live key (written by the scrobble handler, read by `/api/creator/track-status`). The deletion is correct; only the comment is wrong.

### 13. No timeout on any outbound request
- **Severity:** Medium · **Confidence:** Certain (repo-wide search)

Zero occurrences of `AbortSignal`, `AbortController`, or `signal:` across all 27 modules, against ~135 `fetch()` call sites. `fetchWithPerUserCacheAndCircuitBreaker` provides an excellent multi-tier stale fallback (memory → KV → edge cache) — but it only triggers on **rejection**. A provider that accepts the connection and never responds hangs the whole request.

This bites hardest in `prewarmSharedCatalogs`, which awaits ~30 provider calls **sequentially** in the cron: one hung upstream stalls the entire tick, and with a 6-minute schedule the next tick starts before the last finished.

**Fix.** Add `signal: AbortSignal.timeout(ms)` (available in Workers) at the shared helpers — `fetchWithPerUserCacheUncoalesced`'s `fetchFn` call sites and `fetchTraktWithRetry` — rather than at 135 individual sites. 8–10 s for interactive routes, shorter for the cron. **Risk: Low.**

Related naming note: the helper is called a "circuit breaker" but implements no breaker (no failure counting, no open state). A persistently-down provider is still called on every cache miss. Worth either implementing a real breaker or renaming to match what it does.

## Scalability Findings

Behaviour by deployment size, tracing exact code paths:

| Scale | What breaks | Path |
|---|---|---|
| **Any** | Stat counters undercount from the first concurrent request | `bumpStat` (finding 9) |
| **>100 public lists** | Admin "Top Community Lists" reports the wrong lists (KV mode) | `03_admin.js:833` (finding 10) |
| **>1,000 lists per creator** | Watchlist auto-remove silently misses lists | `26_...:410` — no cursor (finding 11) |
| **Any, adversarial** | Admin analytics panel exceeds the subrequest cap permanently | finding 1 |
| **~20,000 public lists** | `index:publiclists` is a single ~4 MB KV value fetched and `JSON.parse`d on **every** search and directory request | `PUBLIC_INDEX_MAX = 20000` |
| **>20,000 public lists** | Lists past the cap silently vanish from search and the directory | `writePublicListIndex` `.slice(0, PUBLIC_INDEX_MAX)` |

**Correctly handled — do not "fix" these:**
- `listAllKeys` (`02_...:1460`) paginates properly with a cursor and `list_complete` check.
- `checkForNewEpisodes` and `/admin/api/backfill-trending` use stored KV cursors with bounded per-run batches — a genuinely good pattern for Worker limits.
- `purgeCreatorData` pages through `creatorlist:{u}:*` with a cursor and does **one** index write for the whole account rather than one per list, correctly citing KV's 1-write/sec/key limit.
- The `index:publiclists` design as a whole is the right call: it replaced an 80–250-key lexicographic scan that made most lists unfindable, and `getPublicListIndex`'s 60-second rebuild lock correctly prevents a stampede on a cold index.

The index's `PUBLIC_INDEX_MAX` truncation is a *documented, deliberate* trade (sorted by likes so the least popular drop first). It is listed here as a scale ceiling to be aware of, not a defect.

## Performance Findings

1. **N+1 KV reads per playback ping** (finding 11) — highest-impact; scales with both list count and ping rate.
2. **`prewarmSharedCatalogs` is fully sequential** (`07_...:1832+`) — ~30 provider calls with `await` in a loop plus explicit 200 ms sleeps, every 6 minutes. Batching with bounded `Promise.all` (as `/api/details/batch` already does with its 6-way worker pool) would cut tick duration by roughly an order of magnitude.
3. **`index:publiclists` parsed per request** — a ~4 MB `JSON.parse` on every search/directory hit at the 20k ceiling. Consider a compact index (arrays not objects) or a per-isolate memo with a short TTL, mirroring `BUILDER_PAGE_MEMO`.
4. **Admin dashboard fan-out** — `renderAdminDashboard` issues `listAllKeys` × 5 plus one `get` per returned key. Finding 10's fix removes ~100 of them for free.

**Already excellent — leave alone:** the `/app.js?v=<hash>` + `/app.css?v=<hash>` content-addressed split with immutable caching and ETag revalidation; `IN_FLIGHT_FETCHES` request coalescing; `renderBuilderCached` / `BUILDER_ETAG_MEMO`; `verifyCreatorKeyMemoized` (a success-only memo that never shortcuts a failed verification).

## DO NOT TOUCH

Code that looks removable or wrong but is load-bearing. Each of these has a comment explaining itself; I verified the reasoning holds.

1. **`getCreator`'s D1-miss → KV fallback** (`02_:1615`). Returning `null` on a D1 miss locks out every account created before `/admin/api/migrate-d1` first ran. A missing row means "not migrated", not "no such user."
2. **`resolveConfig`'s dual path** (`04_:4`). Short-id-then-base64 keeps every pre-KV install URL working. Removing the base64 branch breaks installed add-ons permanently.
3. **The four-variant `keysToTry`** in `/lists/:user/:slug` (`26_:2903`). Raw *and* decoded, creator *and* anonymous — legacy keys were written under different encodings.
4. **`purgeCreatorData`'s legacy key names** (`creatorprofile:`, `creatorpresets:`, `creatorchannels:`). Harmless when absent; without them old accounts leak data on delete. This function exists precisely because reset and delete had drifted apart and "delete my account" once returned `ok:true` while leaving the account fully usable.
5. **`verifyCreatorKeyMemoized`** (`02_:362`). A success-only, per-isolate, hash-keyed memo. A wrong key still pays full PBKDF2, and rotating the key invalidates every entry because the stored hash is part of the memo key. Not a weakening.
6. **`isPublicCorsPath`** (`02_:15`). The narrow allowlist is deliberate — `json()` used to spread CORS onto every response, which made unauthenticated writes callable cross-origin.
7. **The share opt-in gate** in `/lists/:user/:slug` (`26_:2944`), including the strict `=== true`. This route is unauthenticated; a truthy string must not expose someone's viewing history.
8. **`/sw.js`'s cache-first policy.** Safe *only* because it is scoped to content-addressed `/app.js?v=<hash>` and evicts every other entry. Widening it would strand users on stale JavaScript.
9. **`isBrowserNavigation`'s `Sec-Fetch-Mode`-only check** (`02_:145`). The Accept-header signal was removed because wako's webview client sends browser-style Accept on data fetches, silently breaking installs. Do not re-add it.
10. **`getPublicListIndex`'s 60-second rebuild lock** (`02_:1425`). Prevents a rebuild stampede on a cold index; the non-lock-holder deliberately falls through to the bounded scan.
11. **Server/client duplicate pairs** — `isEpisodeAired`, `formatAirDateBadge`, `CHANNEL_ROTATION_*`, `CHART_SLUG_ENTRIES`. Separate runtimes; not consolidatable.
12. **`render_check.js` + `html_checks.py` in CI.** `node --check` on the outer file cannot see the client bundle — it is a template-literal *string* to that parser. This step is the only thing catching a syntax error in `09_`–`24_`.

## FINAL VERDICT

**1. Is this production-ready?**
Not as-is — but it is close, and the gap is narrow and specific. Findings 1–4 are the blockers; each has a fix measured in single-digit lines, and none requires an architectural change. The foundations (auth, authorization, CORS, CSP, OAuth, build reproducibility, caching) are already at production quality.

**2. What would you fix before another user touches it?**
Findings 1–4. Finding 1 because an anonymous attacker can permanently break the admin panel with no recovery path. Findings 2 and 3 because they destroy user data silently, while returning success.

**3. What can wait?**
Everything 🟡: dead code, duplicate `showModal`/`escapeHtml`, `FUNCTION-MAP.md` staleness, the `build.py` header, error-message hygiene. None affects correctness or security today.

**4. Biggest scalability risk?**
The stat counters (finding 9). Not because they fall over — they never fail — but because they under-report by a margin that grows with traffic. The operator's view of the system becomes least accurate exactly when accuracy matters most, and nothing signals it.

**5. Biggest security risk?**
The unauthenticated write endpoints, above all `/api/track-event`. Not credential exposure — I found none — but unbounded, permanent, attacker-controlled writes into shared storage that the admin UI then enumerates.

**6. Biggest architectural risk?**
Read-modify-write on shared KV values as the universal mutation pattern. KV has no compare-and-set, and the codebase already knows this — `applyLikeVote` implements retry-and-verify and its comment explains exactly why. That lesson was applied to one key and not to the others. Findings 2, 3, and 9 are three faces of one architectural gap.

**7. Biggest piece of unnecessary code?**
The five duplicate top-level declarations in the client bundle. Not the largest by line count, but the most *actively harmful*: three of them silently shadow an earlier definition, so editing the shadowed copy changes nothing at runtime and gives no warning.

**8. What is most likely to break as the user base grows?**
In order: the admin analytics panel (subrequest cap, findings 1 and 10) → the stat counters becoming visibly nonsensical (finding 9) → `index:publiclists` becoming a ~4 MB parse on every search → the 20,000-list index ceiling silently dropping lists from search and the directory.
